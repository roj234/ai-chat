# 设计哲学

## 1. 你总是有选择权

本项目所需的外部服务，每一层都可以替换：

| 服务 | 规范 | 参考实现 |
|------|------|----------|
| LLM | OpenAI API | 任何兼容端点 |
| T2I | ComfyUI / A1111 WebUI | [stable-diffusion.cpp](https://github.com/leejet/stable-diffusion.cpp) |
| TTS | 自定义规范（OpenAI + 音色 API） | [qwen3-audio.cpp](https://github.com/Roj234/qwen3-audio.cpp) |
| 数据库 | 自定义 API | `backend/init.js` |
| 文件访问 | 自定义 API | `backend/routes/agent.js` |
| 更多工具 | MCP | 任何 MCP 服务器 |

如果不需要执行命令，就不需要外部文件访问服务，Chrome 的 FileSystem API 足够了。
- 当项目的文件有几千个的时候，还是建议使用文件访问服务（ripgrep），否则一次针对根目录的 Grep 要花费数秒。

如果参考实现满足不了需求，换掉它，而不是让我做我用不上的功能（比如比现在更复杂的鉴权）。
- 换句话说，你要说服我一个功能有意义，我才会添加他，而不是“别人都有”
  - 那你为什么选 AiChat？

## 2. 在需要的时候高级

AiChat 不是"傻瓜式"工具。它默认工作，但始终为深度用户保留入口：

- 展示工具调用的参数和结果
- 各处的【编辑/查看原始数据】按钮
- 基于 JSON Schema 的约束采样管线
- 插件系统和 MCP 支持

## 3. 用户占主导地位

这不是给想让 AI 搬砖的人设计的软件（尽管它确实能做到）。我们是 Agent 的主人，而不是反过来。

### 完全编辑模式

传统 Agent 的工作流是线性的、自动的、不可逆的。
- 模型调用工具 → 出错了？重试，浪费上下文，噪音。
- 上下文偏了？插一条 user 消息，但之前的错误响应和思考已经污染了历史，还可能把模型的思维链给清掉（preserved reasoning）。
- 想改初始消息？请结束对话重新开始。

AiChat 允许你修改任何内容：

- **修改（通常指失败的）工具调用**："就当它成功过"
   - 如果你有耐心，你甚至可以通过复制粘贴的形式假装 Shell 的执行结果
   - 你甚至可以构造工具调用**帮它读取文件**省去缓存读取费用。
- **修改模型的思考过程**：纠正错误推理，而不只是纠正输出
- **修改过去的提示**：让 Agent 即时转变目标
   - 尽管对于 preserved reasoning 的现代模型来说用处不大
- **"理论上来说它是会出现的"**：如果不在，就亲手把它写上
- **对话分支**：在 Chat UI 中经常出现，但在 Agent 中极为罕见。  
做都做了，为什么不让用？知道后果就行（切换分支时工作区不会变化）。
- 用“人类工具”将人变成 Agent 可调用的工具
  - FindDeclaration 让人直接告诉模型函数在哪里，而不需要它自己去读文件搜索。

像调试程序一样调试 Agent 的行为：步进，回退，重试。除了[灵感来源 DsChat](https://github.com/huzpsb/DsChat)，没有任何其他 Agent 项目支持这种工作方式。

### 记忆系统："万物皆文件"

相当一部分（并非所有！）记忆项目都是文件系统的重新发明——用更复杂、更不透明、更难 debug 的方式做增删改查。  
~~*Introducing XX-Memory: A Novel Approach to AI Long-Term Memory Using POSIX-Compliant File I/O*~~

AiChat 选择文件作为记忆系统。

- 没有"做梦"，"忘却"等机制，这些只是对人类的拙劣模仿
- 文件天生支持 组织，namespace、跨平台、零成本、无缝迁移
- 有论文指出 RAG / Vector Database 对编码代理是过度设计：黑箱且无法从错误中学习（无法知道为什么找不到）。文件系统正好在它的反面

*主要是因为懒（Work, then good），语义搜索之后会加的，但以文件为主*  
> 而且你总是可以用 MCP 加入工具，不是吗

## 4. 产品用途不应决定能力上限，它们生来可以组合，应该组合，将会组合。

这是我项目的代价，这是我项目的优点，尽管在弱类型语言中不是那么明显  

### 性能

你看 RojLib 就知道，这是一个二十万行 Java 的巨型 monorepo
它的 core 包包含了我自己设计的 ByteBuffer 和 StringBuilder，它们不使用标准库，而且使用全局缓存和我写的自定义内存分配器  
这不是重点，重点是，没有了翻译开销，例如你要把 JSON 转换为 YAML，`new JsonParser().parse(..., new ToYaml().options(...))`，
